## 产品决策

### P-001 物种原型：黑毛蚁 *Lasius niger*
- **状态**：已采纳（2026-10-21）
- **备选**：切叶蚁（真菌农场、分 4 级体型，分工最丰富，但工作量多约 30%）、收获蚁、不指定物种
- **决定**：黑毛蚁。经典的土栖蚁，研究资料最多，会放牧蚜虫，蚁穴是“小土丘 + 地下多层房间”的结构
- **后果**：工蚁体型基本一致，**没有兵蚁职别**；守卫和防御是工蚁承担的一项任务。工蚁体长取 3–5 mm 的轻微变化（代码中 `size` 为 0.86–1.08）

### P-002 美术风格：风格化低多边形，全部程序生成
- **状态**：已采纳
- **后果**：不需要外部模型和贴图；所有几何都在代码里生成，颜色主要来自顶点色和实例颜色

### P-003 蚁穴呈现：真 3D 地下隧道网络
- **状态**：已采纳
- **备选**：2.5D 蚂蚁工坊式玻璃夹层剖面（更清晰、更省事）、两者都做
- **决定**：真 3D。土壤可以半透明，相机能飞进地下观察
- **后果**：需要一套“从任意角度都能看进空腔”的渲染方案，见 T-010

### P-004 蚁穴生成：预设程序化生成，之后按人口扩建
- **状态**：已采纳；第二阶段实现了扩建（见 T-020）
- **备选**：蚂蚁实时一粒一粒挖掘，蚁穴完全动态生长（难度和性能开销都大）
- **后果**：第一阶段的挖掘只体现在地表土粒上，隧道几何不变；扩建放在第二阶段

### P-005 规模：1000–3000 只
- **状态**：已采纳。第一阶段初始 1000 只，上限 3000（`CONFIG.colony.maxPopulation`）

### P-006 玩家角色：观察 + 轻度干预
- **状态**：已采纳；干预工具放在第三阶段
- **内容**：投放食物、放置障碍、引入天敌、浇水

### P-007 生态要素范围
- **状态**：已采纳
- **做**：昼夜循环、蚜虫放牧、天敌（蜘蛛、蚁狮）、天气
- **不做**：敌对蚁群与领地战争、季节与婚飞

### P-008 交付节奏：原型先行，分阶段迭代
- **状态**：已采纳。三个阶段的内容见 ROADMAP.md

### P-009 项目名：赛博养蚂蚁
- **状态**：已采纳（2026-10-21，第一阶段验收时）
- **背景**：需求方认为原名“蚂蚁生态模拟器”太专业

## 技术决策

### T-001 技术栈：Three.js r170 + TypeScript + Vite，界面用原生 DOM
- **理由**：界面只有几个信息面板，引入 UI 框架不划算；面板每 0.25 秒用模板字符串整体刷新，按钮通过 `data-a` 属性做事件委托

### T-002 尺度：1 世界单位 ≈ 1 厘米，蚂蚁放大到体长 1 单位
- **背景**：真实工蚁只有 3–5 mm，按真实比例在 240 cm 见方的场景里看不见
- **决定**：环境（草高 4–10 cm、房间、深度）按真实厘米尺度，蚂蚁放大约 2.5 倍
- **后果**：信息面板里显示的体长换算回真实毫米（工蚁 `size×4 mm`，蚁后 `size×9 mm`）；房间宽 12–24 cm，最深的越冬室深约 77 cm，与真实黑毛蚁巢的量级相符

### T-003 时间尺度：1 游戏日 = 600 模拟秒，发育期和寿命按比例压缩
- **决定**：1 倍速下 10 分钟过一天，蚂蚁的移动速度接近真实；卵 2 天、幼虫 3.2 天、蛹 2.4 天（约为真实的 1/3）；工蚁寿命 45–90 天（真实约 1 年）
- **模拟步长**：固定 1/30 秒，每帧最多 24 步。20 倍速、60 FPS 下每帧约 10 步

### T-004 模拟层与渲染层分离
- **决定**：`World` 持有全部模拟状态，可以在 Node 中无界面运行（`scripts/games/ant/simtest.ts`）
- **例外**：地形、植被、食物源在构造时就会创建 Three.js 网格。这些只是几何对象，不需要 WebGL，所以 Node 中也能运行
- **后果**：调参时可以快速做无界面回归测试；第三阶段把模拟移到 Web Worker 时，需要先把这几处网格构建挪出模拟层

### T-005 行为模型：生成器协程 + 运动指令两层
- **背景**：要让成千上万只蚂蚁执行多步骤任务（取卵→搬运→放下→整理），而每一步都需要持续若干帧的移动
- **决定**：
  - **行为层**（`sim/routines.ts`）：每项任务是一个生成器函数，通过 `yield` 下达指令，例如 `goto`、`room`、`exit`、`enter`、`search`、`walk`、`patrol`、`wait`
  - **运动层**（`sim/ant.ts`）：每帧执行当前指令，指令完成后才恢复协程
  - 协程结束后，`Colony.newRoutine` 按分工重新选择下一项任务
- **理由**：任务逻辑可以按顺序书写、容易阅读；协程只在指令完成时才被唤醒，开销很小
- **后果**：任务被打断时（例如死亡）调用 `Ant.abort()`；协程恢复后必须重新检查物品是否还有效（`stillMine`），因为世界状态可能已经变了

### T-006 巢内导航：节点图 + Floyd 全源最短路
- **决定**：蚁穴是由入口、分岔点、房间门、盲端组成的节点图，边是隧道（带采样点的曲线）。节点约 22 个，开局一次性算出所有节点对之间的下一跳
- **细节**：蚂蚁贴着隧道底部行走，并按 `lane` 靠右偏移，对向的蚂蚁自然分道；房间内部在地板椭圆上自由走动；位置做指数平滑，避免切换隧道时跳变

### T-007 地表导航：路径整合返巢 + 信息素招募 + 地点记忆
- **依据**：黑毛蚁的真实觅食方式
- **出巢搜索**：
  - 先去记忆中上次找到食物的地点（觅食地点忠诚性）
  - 否则用左、中、右三个点采样路径信息素，偏向远离蚁穴的一侧
  - 都没有就做相关随机游走
  - 7 cm 内能嗅到食物
  - 侦察蚁对信息素的跟随度只有 25%
- **返巢**：路径整合，直接朝巢口走，带随距离减小的方向误差。只有携带食物时才沿途释放信息素，强度随食物源剩余量增加
- **后果**：路径信息素自然形成从巢口到食物源的放射状路径；食物源搬空后路径会挥发消失

### T-008 信息素：单一路径信息素网格
- **状态**：已被 T-022 扩展（新增足迹通道）
- **决定**：240×240 网格（1 cm 一格），半衰期 90 秒，每 0.5 秒统一挥发一次
- **后续**：警报信息素（第三阶段）作为同一网格类的另一个通道加入

### T-009 蚂蚁渲染：实例化网格 + 着色器步态
- **决定**：工蚁和蚁后各用一个实例化网格，一次绘制完。腿部顶点带 `aLeg`（三脚架分组）和 `aHip`（髋关节支点）属性，每个实例的 `aGait` 由行进距离累加，在顶点着色器里绕髋关节摆动腿部；触角也有轻微摆动
- **后果**：阴影里的腿是静止姿态（阴影用的深度材质没有注入这段着色器），可以接受

### T-010 蚁穴空腔用背面渲染
- **决定**：房间、隧道、土壤剖面墙都只渲染背面（`BackSide`）。离相机近的一侧墙自动被剔除，所以从任意角度都能看进空腔，不需要切割平面
- **透视模式**：地表材质改为 16% 透明、不写深度，隐藏草丛和落叶，开启一盏跟随相机的观察灯；相机进入地下或跟随的蚂蚁在巢内时自动开启
- **后果**：拾取房间时射线命中的是远侧内壁，用于选中房间刚好合适

### T-011 拾取：蚂蚁用屏幕空间，其他对象用射线
- **背景**：蚂蚁很小，射线很难点中
- **决定**：蚂蚁按投影到屏幕后的最近距离选取（16 像素容差，距离相机越近越优先）；房间、食物、入口、垃圾堆、石块、植物用射线拾取，地表模式下地形会遮挡射线

### T-012 物品系统：位置状态 + 认领
- **决定**：卵、幼虫、蛹、食物、垃圾、土粒、尸体统一用 `Item` 表示：
  - `place` 记录物品在哪里：房间、隧道节点、地表、垃圾堆、蚁丘、被携带、已销毁
  - `claimedBy` 防止多只蚂蚁去取同一件物品
- **后果**：任何“取东西”的任务都要先认领、到达后再确认；放弃任务时必须释放认领

### T-013 经济平衡依靠负反馈
- **背景**：调参中先后出现过饿死崩溃和食物无限堆积（见 BALANCE.md）
- **决定**：
  - 储备越多，觅食蚁越倾向于留在巢内（真实蚁群也会这样调节觅食量）
  - 储存的食物会变质：猎物和种子变成垃圾，甜液干涸
  - 进食失败后冷却一段时间，避免死循环
- **后果**：系统自稳定。以后增加新的食物来源或消耗时，要在 `simtest` 里确认储备不会单向漂移

### T-014 验证方式：无界面模拟 + 无头浏览器截图
- **决定**：
  - 行为和平衡用 `scripts/games/ant/simtest.ts` 验证
  - 画面用无头 Chrome 截图验证，配合 `scripts/tools/extract-shots.mjs` 从捕获结果中提取图片
- **限制**：浏览器自动化工具不支持鼠标拖拽，鼠标交互需要人工测试

### T-015 URL 参数
- **决定**：提供 `?cam=`、`?select=`、`&follow=1`、`&fly=1`、`?hour=` 五个参数（用法见 README），既方便分享观察视角，也用于截图验证
- **第二阶段补充**：`?skip=秒数`（开局在后台快进模拟，上限 20000 秒）、`?view=xray,pheromone,roles,stats`（开局打开显示开关）、`?select=plant:N`。`hour` 改为“快进到下一个该时刻”，可以和 `skip` 一起用

### T-023 发布形态：单个 HTML 文件，双击即可运行
- **状态**：已采纳（2026-10-21，需求方希望不需要服务器）
- **背景**：浏览器禁止从 `file://` 加载外部的 `<script type="module" src>`，普通 Vite 产物必须通过 HTTP 服务器打开
- **决定**：`vite.config.ts` 里的 `singleFile` 插件在打包后把 JS 和 CSS 内联进 `index.html`，并删除原来的分块文件；关闭 modulepreload 和 CSS 拆分，动态导入全部内联。没有引入第三方插件
- **发布文件**：构建时同时写一份到项目根目录 `cyber-ant-farm.html` 并提交进仓库，方便直接下载双击。用不同的名字是为了和根目录的源码模板 `index.html` 区分。原名 `赛博养蚂蚁.html`，后改为英文名：中文文件名在命令行、git 输出和部分下载工具里会变成乱码或转义
- **前提**：项目没有任何外部素材（P-002），所以单文件就是全部内容。以后如果加入图片、音频等文件，需要转成 data URL 内联，或者放弃这种形态
- **后果**：开发时仍然用 `npm run dev`；第三阶段如果把模拟移到 Web Worker，Worker 也要用 Blob URL 内联创建，不能用独立文件

### T-016 分工模型：行为年龄排序 + 按需目标
- **背景**：第一阶段新羽化的工蚁全部是保育蚁，分工比例会漂移（真实蚁群是年龄多型性 + 按需弹性调整）
- **决定**：
  - 每只工蚁有“行为年龄” = 日龄 + 个体随机偏移（标准差 `polyethism.ageJitterDays`），代表发育快慢的个体差异
  - 每 `reviewDays` 计算一次目标：保育蚁随幼体数增加；觅食蚁比例随“储备够吃几天”在 58%–40% 间变化；剩下是内务蚁（至少 14%）
  - 工蚁按行为年龄从小到大依次对应保育→内务→觅食。正向转换按需发生；逆向转换（例如觅食蚁回巢当保育蚁）只在缺口超过 15% 时发生
  - 每次评估最多转换 `maxShift`（2%）的工蚁；转换记为 `nextRole`，等当前任务结束后才生效
- **后果**：分工比例自稳定，实际人数紧跟目标；觅食蚁大量死亡时会出现“较年轻的工蚁提前转为觅食蚁”事件。信息面板显示“即将转为 X”

### T-017 社会胃：液体食物只存在于嗉囊
- **背景**：真实黑毛蚁不在房间里储存液体，甜液在工蚁的嗉囊里，通过交哺在群体内流动
- **决定**：
  - 每只工蚁有 `crop`（0–1）。储食室只放固体（猎物碎块、种子）；“社会胃”是所有嗉囊之和，只用于显示和决策，不单独存储
  - 饥饿的蚂蚁先喝自己嗉囊里的，再向同房间嗉囊较满的同伴乞食（交哺时两只都停下面对面）；保育蚁在喂幼虫前也会先乞食
  - 归巢的觅食蚁在入口附近房间把蜜露分给多只同伴（`unloadCrop`）；嗉囊满的内务蚁会把甜液分给其他房间（`distributeCrop`）
- **后果**：甜液不会变质（第一阶段的“甜液 4 天干涸”规则随之取消），但总量受嗉囊容量限制，起到自然上限的作用。储备 `reserve` = 固体 + 社会胃

### T-018 接触检测：每帧重建的均匀空间哈希
- **决定**：`SpatialHash` 格子 2 cm、8192 个桶，每个模拟步用链表重建（O(n)）。每只蚂蚁每 8 步检测一次 0.9 cm 内的同伴，接触成功后双方停顿 0.6–1.3 秒、互相转向，冷却 6–16 秒
- **用途**：触角接触统计；满载归来（正在释放路径信息素）的觅食蚁会“激发”巢内的觅食蚁，被激发者 90 秒内更倾向出巢（夜间留巢、饱食抑制都会减弱）
- **后果**：加入接触检测后，1000 只时每步总耗时仍在 0.35 ms 左右。第三阶段的碰撞、天敌感知可以复用同一个哈希

### T-019 向阳育幼室与蛹的温度调节
- **背景**：黑毛蚁常在石块下筑巢，白天把蛹搬到被晒热的石块下方加速发育
- **决定**：大石块下方新增浅层房间（深约 7 cm）。石块加温 = `stoneHeat × max(0, sin(正午相位)) × (1 − 深度 / stoneHeatDepth)`。每 0.01 天比较蛹室和向阳育幼室，评分以 30°C 为最佳，差距超过 1.2°C 才切换（防抖），切换后把所有蛹标记为待搬运
- **后果**：蛹的发育速度随温度变化（系数 0.6–1.3）；面板与事件中能看到“升温到 X°C，保育蚁开始把蛹搬上来”

### T-020 扩建：隧道工作面 + 渐进生长的房间
- **决定**：
  - 占用率 = (成虫 + 幼体) / Σ(rx·rz·`capacityPerArea`)。超过 `trigger` 时规划一间新房间（幼体多则是幼虫室，否则是休息室），在深于 8 cm 的分岔点附近随机找不与现有结构重叠的位置
  - 先挖隧道：工作面 `DigFace` 的边是规划路径截断后的一段，末端节点随挖掘前进，每挖 1 粒土延长 0.25 cm，并重算寻路
  - 隧道挖到后变成新房间的门，房间以 `ready = false` 加入，`grow` 从 0.08 涨到 1；未完工的房间不参与“按类型找房间”和定位
  - 最多 18 只内务蚁同时在一个项目上挖掘；每次挖出的土粒照常运到地表蚁丘
- **后果**：`Nest.rev` / `edge.rev` 递增时视图重建对应网格；土壤剖面墙按新的包围盒重建。房间生长时网格从门口位置缩放展开

### T-021 蚜虫：附着在植物上的种群，带放牧忠诚性
- **决定**：
  - 蚜虫群附着在植物茎秆的一段高度上，Logistic 增长：被照料（90 秒内有蚂蚁来过）时增长率 0.35/天，否则 0.1/天并有 0.08/天的损失；蜜露按数量累积到上限
  - 觅食蚁在搜索中发现有蜜露的蚜虫群就爬上茎秆，采集到嗉囊里，返巢时释放信息素；采过的蚂蚁会以 80% 概率回到同一群（放牧忠诚性）；没有蜜露时会停在上面“守护”25–45 秒
  - 蚜虫数量变化时才重写实例矩阵
- **后果**：蜜露成为社会胃的主要来源；第三阶段的瓢虫可以直接攻击这些蚜虫群

### T-022 信息素第二通道：领地足迹
- **决定**：所有在地表的工蚁每秒沉积 `depositHome`，半衰期 900 秒（路径信息素的 10 倍）。侦察蚁前方足迹浓度大于 0.3 时转向足迹最少的方向，从而倾向探索新区域
- **热力图**：足迹为蓝色底层，路径信息素按浓度从橙红到亮黄叠在上面（标准的 over 合成）；纹理标记为 sRGB、关闭色调映射，避免颜色发白；开启时右下角显示图例

### T-024 玩家干预：World 方法 + 试运行
- **决定**：所有干预都是 `World` 上的方法，返回 `{ok, msg}`；传 `dry` 时只检查不执行。界面的预览圈直接用试运行结果变色，提示文字和真正放置时的拒绝理由完全一致
- **原因**：模拟层保持不依赖 DOM（之后存档、Web Worker 也只需要序列化这些调用）；检查逻辑只有一份
- **限制**：不能堵住入口（入口 4 cm 内不能放）、不能超出活动范围、不能和石块 / 植物 / 水洼 / 食物重叠；只能移除玩家自己放的障碍物
- **地面点**：鼠标下的地面点沿视线对解析高度场 `heightAt` 步进再二分，不对地形网格做射线检测（网格很大，而且草会挡住射线）

### T-025 水洼是“软”障碍物
- **决定**：水洼登记在避障网格里，但蚂蚁移动时不把它当成硬障碍：先沿边绕行，4 秒内绕不开就蹚水通过，速度降到 35%
- **原因**：硬障碍的水洼会永久挡住入口或食物（`walk` 指令没有超时），而真实的蚂蚁遇到浅水也会涉水。水洼会冲刷信息素、随温度蒸发收缩，几分钟后蚂蚁重新铺出路径

### T-027 存档：只存会变化的状态，读档通过重新载入页面完成
- **存什么**：地形、植被、初始蚁穴、蚜虫群的位置都由世界种子决定，不写进存档；写进存档的是蚁穴结构（扩建后会变）、全部蚂蚁和物品、食物源、蚜虫群状态、两个信息素通道（量化为 8 位后 base64）、玩家放的障碍物和水洼、相机视角。存档带版本号和种子，版本不匹配时放弃读取并开始新的蚁群；读档时用存档里的种子重新生成世界（T-035）
- **行为协程不保存**：生成器无法序列化。读档后每只蚂蚁的任务从头开始；走在隧道中途的放到最近的节点，爬在植物上的放回地面，正在搬运的物品直接送到目的地（幼体、食物、垃圾进对应房间，尸体到垃圾堆，土粒丢弃），认领关系全部清空。代价是读档瞬间储食室会多出几十份“在路上”的食物（后来改为物品留在蚂蚁嘴里、读档后接着送，见 T-059；正在做的那一步接着做完、不再放回节点和地面，见 T-067）
- **读档 = 重新载入页面**：存档在页面启动时、创建任何视图之前套到刚生成的世界上，视图按读档后的结构从头建立，不需要处理运行中替换蚁穴网格、实例数量等问题。“读取上次存档”和“重新开始”都是重新载入，载入前禁止自动保存以免覆盖
- **存储**：`localStorage`，同步写入，关闭页面（`pagehide`）时也能可靠保存。1000 只蚂蚁时约 1 MB，蚁群长到 3000 只时预计 2–2.5 MB，在浏览器约 5 MB 的配额以内；写入失败时提示玩家。没有用压缩（`CompressionStream` 是异步的，关闭页面时来不及完成）
- **存档代码的位置**：各子系统自己实现 `toSave` / `restore`（需要访问私有字段），`world/save.ts` 负责组装和版本检查，`ui/saveSlot.ts` 负责读写 `localStorage`，模拟层不接触浏览器 API

### T-028 天敌：狼蛛与蚁狮，取代随机的地表意外死亡
- **决定**：去掉“地表蚂蚁每天 3% 意外死亡”，改为两种看得见的天敌，统一放在 `world/predators.ts`（`PredatorManager`），捕食通过 `Colony.kill(ant, cause, false)` 结算，计入 `stats.preyed`
  - **狼蛛**：从觅食范围边缘游荡进来（每天约 1.2 只，同时最多 2 只自然狼蛛），走向范围内随机的目标点，并顺着足迹信息素浓的一侧转向（足迹反映地面上蚂蚁来往的多少，相当于感知振动）。7 cm 内发现蚂蚁就冲刺扑击，60% 成功；进食 90 秒后留下空壳。停留 0.4–0.8 天或吃够 3 只后离开
  - **蚁狮**：开局在距巢 18–75 cm、草少的裸地上有 3 个陷阱。陷阱是一块“松沙”区域：蚂蚁在里面速度降到 40%，同时被拉向中心，越靠中心越陡；进坑 0.6 秒后蚂蚁会转身往外爬。滑到中心就被抓住，进食 4 分钟后把空壳甩出坑外。进食期间不扬沙，坑壁拉力降到 35%，后来的蚂蚁都能爬出去
- **原因**：随机死亡玩家看不见、也没法应对；天敌能被观察、被放入和赶走，第四项“警报信息素与防御”也需要一个具体的攻击者
- **空壳**：作为普通尸体物品留在地表，内务蚁会把它搬去垃圾堆，不需要新的物品类型
- **陷阱的高度**：地形网格建好后不再改动，陷阱做成中心贴地、四周堆起的沙环，靠颜色由浅到深表现漏斗；地表蚂蚁的高度会加上沙面抬高量（`PredatorManager.liftAt`）
- **存档**：天敌位置和状态写进存档的可选字段 `predators`；旧存档没有这一项时沿用新世界自然生成的蚁狮，不需要升级版本号
- **数值结果**：5 个游戏日约 30 只被捕食（其中蚁狮约 60%），与原来的意外死亡量级相当，蚁群照常增长

### T-029 警报信息素与工蚁防御
- **警报信息素**（`world/alarm.ts`）：点源列表，不是网格。只在受攻击的少数地点出现、几秒就散（半衰期 6 秒），浓度 = 强度 × 距离线性衰减（半径 10 cm）。2 cm 内的新释放并入已有点源
- **谁会响应**：地表上没有搬东西、没在爬植物、没陷在坑里的工蚁，每 0.5 秒闻一次，浓度超过 0.15 就暂停当前任务去增援 15–30 秒（`Ant.defend`，与 `hold` 一样在 `update` 开头接管，不打断协程，结束后原任务接着执行）
- **围攻**：附近 12 cm 内有狼蛛就冲过去，贴身后原地撕咬并持续补充警报，于是招来更多同伴（正反馈）。狼蛛的“被咬程度”按 工蚁数 × 秒 累积，超过 14 就丢下猎物逃走；被 2 只以上围住时不再扑击。每只撕咬的工蚁每秒有 2.5% 的概率被咬死
- **入口警戒**：狼蛛离某个入口 20 cm 以内时，准备出巢的觅食蚁 70% 留在巢里；内务蚁 50% 去那个入口外巡逻（同时最多 24 只）。日常的入口巡逻照旧，不计入这个上限
- **蚁狮**：陷阱里不释放警报，否则同伴会被招进坑里。改为个体学习：爬出过陷阱的蚂蚁记住位置，之后绕开；目标就在坑里时绕 6 秒后放弃回避
- **不存档**：警报、增援状态、狼蛛的被咬程度和蚂蚁记住的陷阱都是几十秒内的短暂状态，读档后清空（后来蚂蚁身上的增援、躲避和记住的陷阱进了存档，见 T-067；地面上的警报浓度和狼蛛被咬的程度仍不存）
- **结果**：觅食路线上放一只狼蛛，通常吃到 1 只后几秒内被赶走（3–4 只贴身围攻，10 余只赶来增援）；放在巢口时 20–30 只围攻。自然情况下 5 个游戏日约有 2 只狼蛛被赶走，蚁狮的捕获量也因为绕行略有下降

### T-030 天气：下雨、封堵入口与浅层进水
- **状态**（`world/weather.ts`）：晴 → 转阴 → 下雨 → 晴三个阶段，每个游戏小时按 `rainPerDay / 24` 的概率转阴；另有平滑过渡的雨势、云量，以及地面湿润度（下雨时上升，雨停后按温度和云量晾干）。第一天不自然下雨
- **作用方式**：天气不直接改其他系统的逻辑，而是写进它们已有的入口：`SimClock.weatherCool / groundWet`（温度、湿度）、`PheromoneField.rain`（消散速度，两个半衰期按雨势叠加）、`water.pour`（积水洼）、`Ant.speedFactor`（地表减速）、`Chamber.wet`、`Entrance.plug`
- **躲雨**：进入转阴 / 下雨阶段时，`Colony.seekShelter` 按概率中断地表空手工蚁的协程（清掉认领后 `abort`），`newRoutine` 在天气不好时给地表工蚁安排“返巢 → 休息”。搬着东西、爬植物、打斗、陷在坑里的不打断，做完手头的事自然会回巢
- **封堵入口**：真实的黑毛蚁会在雨前和夜里用土粒堵住巢口。转阴后内务蚁优先领取封堵任务（`WeatherSystem.plugJob`，按入口剩余工作量减去已在路上的工蚁分配，每个入口最多 4 只），走到入口节点干 3–5 秒，封堵 +20%；雨停且地面湿润度低于 0.45 时同样方式清开（T-036 改了这些数值）。`plug = 1` 的入口不能出巢（`stepExit` 改走其他入口，全封时在入口里等），进巢不受影响
- **封闭期的巢内工作**：觅食蚁留巢，内务蚁只做巢内清理、分食和巡视；挖掘照常进行，但挖下的土压在隧道壁上，不往外运（否则会有上百只搬着土的工蚁堵在入口）
- **进水**：每间就绪的房间按 雨势 × 入口平均敞开程度 × (1 − 深度/14 cm) 进水，同时以固定速度渗干。积水 ≥ 0.25 的房间不参与蛹室的温度选择（正在里面的蛹立即改为搬走），储食变质加快 3 倍。只有储食室、垃圾室、向阳育幼室在 14 cm 以内
- **画面在模拟层之外**：雨丝（`render/rain.ts`）是在相机与注视点之间循环下落的线段，盒子大小随观察距离缩放；云量传给 `Environment.update` 调暗天空和阳光；地面材质随湿润度变深。土塞和积水面由 `NestView.sync` 按 `Entrance.plug` / `Chamber.wet` 显示
- **存档**：可选字段 `weather`（阶段、计时、雨势、云量、湿润度、各入口封堵、各房间积水），旧存档没有时为晴天

### T-031 性能：不用 Web Worker，改做缓存、细节层级和帧预算
- **测量**（`scripts/games/ant/perftest.ts`，3000 只工蚁）：优化前每个模拟步 1.74 ms，95% 花在 `colony.update`；剖析显示最贵的是逐只蚂蚁调用的解析式地形高度 `Terrain.heightAt`（多层正弦和蚁丘求和）和随深度计算的温度速度系数
- **决定**：
  - 地形高度在建网格时预先采样成 0.5 cm 间距的网格，之后双线性插值查表（建网格本身仍用解析式）
  - 蚂蚁的温度速度系数缓存 0.5 秒，同一位置域内不重复计算
  - 远处工蚁（离相机超过 `ant.lodDistance` = 35 cm）改用简化网格：286 个三角形，完整网格是 1008 个；不投影。被选中的蚂蚁始终用完整网格
  - 每帧模拟最多 `time.frameBudgetMs` = 10 ms，超出就丢掉没算完的时间；顶栏性能信息显示“实际 x×”
- **结果**：每步 1.74 → 约 1.0 ms。无头 Chrome 中 3000 只：20 倍速 60 FPS，模拟 10.3 ms/帧（基本达到 20 倍速），10 倍速透视 60 FPS、模拟 5.9 ms/帧，提交渲染约 2 ms
- **为什么不用 Web Worker**：模拟层里有几处直接持有 Three.js 网格（地形、植被、狼蛛等，见 T-004 的后果），要先拆开；渲染每帧需要读取所有蚂蚁的位置、朝向、步态，要设计共享缓冲区；存档、点选、信息面板都直接读模拟对象，都要改成消息。测量表明主线程在 20 倍速下仍有余量，改造收益小于成本
- **备选**：如果之后规模扩大到 1 万只以上，或者要支持低端设备的高倍速，再考虑 Worker（Blob URL 内联，见 T-023）

### T-032 蚂蚁之间保持间距：推开与横向让行，不做硬碰撞
- **问题**：蚂蚁之间原来没有碰撞，1000 只时同时有约 600 对蚂蚁身体重叠（中心距 < 0.45 cm），大部分在隧道里：同时出发、速度相同的蚂蚁在相近的车道上一路叠在一起走
- **地表和房间**：相距不到 2 × `ant.personalSpace`（0.64 cm）就互相推开，蚁后按体型算。走动中的蚂蚁每秒最多被推 0.18 cm，停着的 0.6 cm：走动中的推力小于步速，保证带目标点的指令（`room` 的 `point`、地表 `walk`）一定能走到，停下来休息、等待的蚂蚁则会散开。推开后落在障碍物里或房间地板外就不推
- **隧道**：隧道里的蚂蚁按所在的边分组、按沿边位置排序，只比较前后 `ant.tunnelGap`（0.9 cm）以内的同伴，横向相距不到 0.4 cm 就各自往旁边让（改变车道偏移 `side`，最多到隧道半径的 0.55 倍）。会车和超车都这样处理，不会停下来
- **个体步速**：巢内步速乘以每只蚂蚁固定的 0.88–1.12，同时出发的同伴会慢慢拉开
- **试过但放弃的**：隧道里跟车（同向的前车太近就退回、等 1.5 秒后再挤过去）。结果交通变慢，隧道里的蚂蚁从约 370 只增加到 560 只，重叠反而更多
- **开销**：每只蚂蚁查一次空间哈希约 0.5 µs，所以隧道里改用按边排序，不查哈希；房间和地表每 6 步轮换检查一次。空间哈希的网格从 2 cm 改为 1 cm
- **结果**：1000 只时重叠从地表 15–23 对、巢内 540–760 对降到 7–10 对、250–300 对；3000 只时减半。剩下的主要是比隧道宽度还密的车流、房间里走动中的蚂蚁，以及停在路口和房间门口的蚂蚁（路口不处理）。每步耗时 1000 只 0.21 → 0.29 ms，3000 只约 0.9 → 1.5 ms（无头 Chrome 中 3000 只、20 倍速时实际 12 倍，60 FPS）

### T-033 扩大已有房间：以门口为不动点放大
- **问题**：扩建只会新增房间，房间数到 `expansion.maxChambers`（22）后蚁穴就不再长大；真实的毛蚁巢也会把常用的房间越挖越大
- **几何**：以房间门口的水平位置为不动点做位似放大，地板中心和 `rx`、`rz` 乘以 `expansion.enlargeScale`（1.2），高度 `ry` 不变。门口在原地板内，所以放大后的地板包含原来的地板：已经放在房间里的物品、正在房间里的蚂蚁都不用移动，门口仍然在墙上
- **选房间**：只考虑卵室、幼虫室、蛹室、储食室、休息室（蚁后室、垃圾室、越冬室、向阳育幼室的位置有特殊含义），按每单位面积的蚂蚁数排序，取第一间 `Nest.canEnlarge` 通过的：放大后与其他房间相距 2 cm、与不经过自己门口的隧道相距 1.2 cm，距巢中心 40 cm 内，半径不超过 12 cm
- **挖掘**：复用扩建项目，工作面是房间门口；每粒土按比例插值地板中心和半径，需要的土粒按新增面积计算。房间一直 `ready`，蚂蚁照常使用
- **渲染**：不重建房间网格，按建模时的半径非均匀缩放；完工时 `nest.rev++` 更新土壤剖面墙的范围（剖面墙外扩 8 cm，一次扩大最多外移约 4 cm，过程中不会露出）
- **何时扩大**：需要扩建时 40% 的概率先尝试扩大（`expansion.enlargeChance`），没有合适的房间就规划新房间；房间数到上限后只扩大

### T-034 地表热闹度：待命的觅食蚁在巢口附近闲逛
- **问题**：巢外的蚂蚁数量由饱食抑制决定，和收入绑在一起。调参历史（BALANCE.md）里放宽抑制后巢外能到 110–250 只，但储备涨到约 1000 份；收紧后只剩 60–100 只。1000 只的蚁群白天巢外平均只有约 150 只
- **决定**：饱食抑制命中、本来要回休息室待命的觅食蚁，白天天气正常、地表不低于 14°C、巢口没有狼蛛时，45% 改为出巢闲逛：在离入口 2–7 cm 的地方用入口警戒的 `patrol` 指令走走停停 30–80 秒，然后回巢。闲逛不搜索食物，也不带东西回来，所以不增加收入；真实的黑毛蚁在天暖时巢口附近也常有闲逛的工蚁
- **没有选的**：放宽饱食抑制并加快变质（经济会跟着变，需要重新调平衡）；延长每趟觅食时间（改变觅食效率和分工比例）；提高开局数量（蚁群“从小长大”的感觉变弱）
- **结果**：10 个游戏日里，白天巢外平均 148 → 251 只、最多 391 → 478 只，其中闲逛约 100 只；采集量少约 4%，人口、死亡数在随机波动范围内。巢口附近蚂蚁多，狼蛛在主入口外时增援更多、更快被赶走。每步耗时 1000 只 0.29 → 0.36 ms，3000 只 1.57 → 1.66 ms

### T-035 新开局随机生成地图
- **问题**：世界种子固定（`CONFIG.seed`），每次新开局的地形、石块、植物、食物和第二天的天气都一样
- **决定**：新开局用随机种子，`World.seed` 记下它，存档保存这个种子，读档时用它重新生成世界再套上存档。网址参数 `?new=1&seed=编号` 可以用指定地图开局，存档面板显示地图编号。之前的存档种子都是 `CONFIG.seed`，仍然可以读取
- **验证**：随机生成 40 个种子的世界，房间类型齐全、两个入口、6 群蚜虫、12 个食物源，没有失败的；随机种子世界的存档往返一致
- **不变的**：脚本测试和 `new World()` 仍然默认用 `CONFIG.seed`，测试结果可以和以前对比；蚁穴是模板加随机扰动，所以每张地图的蚁穴结构相似

### T-036 下雨体验：封得更快、雨后分批出巢
- **问题**：玩家招雨时只转阴 8 秒，内务蚁来不及封入口，浅层房间几乎每次都进水（测试中最大积水 0.38）；雨停后要等地面湿润度降到 0.45 才重开，夜里一场雨后蚁群停摆约 250 秒现实时间；入口封住时正搬着土粒、垃圾往外运的内务蚁一直堵在入口里等（最多 24 只）
- **封堵**：玩家招雨时转阴最多 20 秒（`calledOvercastSec`）；每次封堵 25%，每个入口最多 6 只同时干；领到任务的内务蚁在同一个入口一直干到封好（或清开）为止，不用每填一层就重新走一趟。每次招雨大约 20–50 秒封住两个入口
- **进水**：进水量再乘以随地面湿润度从 0.2 到 0.6 平滑升高的系数（`runoffWet`），刚下雨时雨水先渗进土里。入口按时封好时房间基本不进水；进水主要发生在内务蚁不够、或者入口封得慢的时候
- **雨后**：地面湿润度降到 0.7 以下就清开入口，侦察蚁先出去；其余觅食蚁按 `WeatherSystem.damp`（湿润度从 0.7 降到 0.4 时从 1 降到 0）的概率继续留巢，蚁群陆续恢复出巢，而不是一下子全部涌出；地面还湿时没有闲逛（T-034）。晾干基准从 240 秒缩短到 180 秒
- **入口封住时**：`exit` 指令加 `giveUp`，所有入口都封死时立即以 `'blocked'` 结束而不是等待。运土的内务蚁把土粒压在隧道壁上，运垃圾、尸体的放进垃圾室，等入口重开后再运出去。觅食蚁、闲逛的蚂蚁仍然在入口里等
- **结果**：夜里招雨，入口 17–38 秒全部封住，浅层房间不进水，雨停后约 130 秒重开（原来 250 秒），最多 2–5 只等在入口；白天招雨 53 秒封住，雨停后约 90 秒重开

### T-037 蚁狮坑挖进地面；雨中的水花与植物
- **问题**：蚁狮坑原来是盖在地面上的沙环（中心贴地、四周堆高），因为地形网格建好后不再改；下雨时只有雨丝，地面没有溅落，植物也不动
- **坑**：`Terrain.setDent` 只改显示网格的顶点，把坑内的顶点压到坑面以下，坑面另做一个更细的漏斗网格盖在上面（坑深 1.5 cm，坑口一圈略高的松沙）。地形网格的三角形约 1.1 cm，比坑小得多，所以压低量要留余量：漏斗中心尖，三角形的弦会高出坑面，越靠中心余量越大。用射线检查 4000 个点，地面都在坑面以下。`heightAt` 不变，模拟（高度表、蚂蚁、狼蛛）不用改；坑里的东西照旧叠加 `liftAt`，现在是负值，蚂蚁会滑到坑底。蚁狮被移除（读档、填平陷阱）时把顶点恢复原样。信息素叠加层是地形网格的拷贝，登记后跟着一起变形
- **落叶**：落叶贴着原地面摆放，坑挖下去后会横在坑上，所以放蚁狮时去掉坑附近的落叶（填平后不补回）
- **水花**：雨势大于 0.02 时，在注视点周围随机位置生成扩散的小水圈（线段画的 8 边形，带逐顶点透明度），每秒数量只和雨势有关，范围和大小随观察距离变化
- **植物**：叶片改为挂在茎上的挂点下，下雨时被雨压低，雨滴随机打中时上下颤动（阻尼弹簧）；茎不动，爬在茎上的蚂蚁和蚜虫的位置不受影响。草叶摆幅和速度随雨势增大。都用 `Math.random`，不消耗世界随机数

### T-038 房间门口拥挤：交哺前先走进房间
- **测量**：1000 只时巢内重叠约 200 对，八成在隧道里；停在路口的只有约 2 对，所以路口不用处理。房间里的重叠有四分之一在门口 1 cm 内；储食室约 30 只蚂蚁里有 12–15 只在门口 3 cm 内（门口附近只占地板面积的约 7%），其中一半在交哺
- **原因**：返巢卸甜液、把甜液带到育幼室的蚂蚁进门后只走 0.3–1.5 秒就开始交哺，而 `findRoommate` 找最近的同伴，找到的多半是同样刚进门的蚂蚁，于是在门口越聚越多
- **决定**：交哺前先走到房间地板上的随机位置（`walkIntoRoom`）。其他进房间的指令本来就会走到随机点，不用改
- **结果**：储食室门口 3 cm 内 12–15 → 4–10 只，门口不再有交哺的团；交哺次数少约 5%，人口、采集量在波动范围内。3000 只时房间重叠主要在休息室（200 多只待命的蚂蚁挤在两间休息室），属于房间容量问题，没有处理

### T-039 点击事件跳到发生的地方
- **数据**：`Colony.pushEvent(msg, ref?, at?)`。`ref` 是事件涉及的对象（蚂蚁、房间、入口、食物源、植物、天敌、玩家障碍物），`at` 是事件发生时的位置，省略时取 `ref` 当时的位置。天气这类全局事件两者都没有，不能点击
- **点击**：对象还在就选中它并飞过去（和双击一样，地下的会自动切到透视）；不在了（蚂蚁死了、狼蛛走了、食物搬完了）就飞到 `at`，并提示“它已经不在了”
- **存档**：狼蛛、蚁狮、食物源、玩家障碍物的编号读档后会重新分配，存档时去掉这几类的 `ref`，只留位置；蚂蚁、房间、入口、植物的编号读档后不变
- **界面**：事件列表常常刷新，在两次刷新之间按下、松开鼠标，`click` 会因为元素被替换而丢失，所以列表只在事件变化时重写，并用 `pointerdown` 响应

### T-040 中英文界面：延迟翻译的文字
- **需求**：把写死的文字抽出来，支持中文和英文；第一次打开自动选语言，游戏中可以随时切换
- **词典**：`zh.ts`（现在在 `src/games/ant/i18n/`）是键的来源，`en.ts` 的类型是 `Record<MsgKey, Entry>`，缺键时编译报错。参数写成 `{name}`；英文要按数量变单复数、或句子以参数开头要大写时，词条写成函数。英文名词在词典里小写（“food store”），界面放在标题和行首时由 `hud.ts` 的 `cap` 大写首字母
- **延迟翻译**：模拟层不拼字符串，只记下键和参数（`Text = { k, p }`，参数里可以嵌套 `Text`，比如“前往{room}”里的房间名）。蚂蚁的当前行为、个体日志、蚁群事件、工具结果都是 `Text`，界面显示时才按当前语言翻译，所以切换语言后已经产生的事件和日志也会跟着变。模拟层仍不依赖 DOM，Node 里默认中文
- **房间和入口的名字**：不再存拼好的“储食室 2”，而是类型 + 同类第几间（`Chamber.ordinal`），显示时组合
- **存档**：事件和日志的时刻改存模拟秒数，存档摘要存 `seconds`，显示时按当前语言格式化。旧存档里拼好的中文（事件、日志、摘要时刻）用 `raw` 词条原样显示；旧存档的房间名从末尾的数字取回编号。日志从字符串变成对象后，1000 只蚂蚁的存档约大 70 KB（蚁群 830 → 900 KB）
- **选择语言**：网址 `?lang=` > 玩家上次手动选择（`localStorage` 的 `cyber-ant-lang`）> 浏览器首选语言（`zh` 开头用中文，其他都用英文）。`?lang=` 不会被记住，用于截图
- **切换**：顶栏右上角的语言菜单（T-041），`Hud.relocalize` 重写顶栏、帮助、图例，并清掉工具面板、存档面板、事件列表、统计曲线的缓存，随后立刻刷新一次
- **排版**：英文标签更长，`html:lang(en)` 时蚁群概况和事件列表放宽

### T-041 顶栏分两行，语言改为下拉菜单
- **需求**：顶栏太乱；GitHub 和语言要固定在最右侧；语言改成下拉，方便以后加语种
- **问题**：原来所有按钮组排在一行里自动换行，换到第几行取决于窗口宽度和语言，右侧的存档、语言、GitHub 跟着漂移；每个按钮都带快捷键角标，显得很碎
- **决定**：固定两行
  - 上行是状态：标题、时间天气，右侧依次是性能数字、帮助、存档、语言菜单、GitHub（帮助原在下行最右，T-042 加入“后台运行”后移到上行）。性能数字可以被截断（悬停看完整），所以右侧几个入口始终停在最右
  - 下行是操作：速度、视图、工具三组，每组前面有小标签。窗口太窄时工具组折到下一行
  - 窗口宽度不到 1500 px 时隐藏快捷键角标（悬停提示和帮助面板里仍有），不到 1200 px 时隐藏物种名
- **语言菜单**：自己画的弹出菜单，不用原生 `<select>`：原生下拉框收起后仍保持焦点，按 E（相机下降）这类字母键会直接选中 English。菜单里的语言名用各自的写法（中文、English），点菜单外面收起

### T-042 后台运行
- **需求**：最小化浏览器后游戏就停了；加一个开关让它在后台继续运行，默认开启
- **原因**：不是有意的设计。主循环靠 `requestAnimationFrame` 驱动，浏览器对隐藏的页面（最小化、切到其他标签页）不再调用它；回来后第一帧的时间差又被限制在 0.1 秒，所以离开期间的时间整段丢掉
- **做法**：页面隐藏且开关打开时，`BackgroundRunner` 接手推进模拟，只算模拟和自动保存，不渲染
  - 节拍来自一个很小的 Worker（Blob 生成，单文件 HTML 也能用）。后台页面里主线程的 `setInterval` 会被浏览器降到每秒一次，隐藏 5 分钟后再降到每分钟一次；Worker 发来的消息不受这些限制。Worker 建不起来时退回 `setInterval`，按实际经过的时间补算
  - 后台模拟最多占用 40% 的时间（`backgroundCpuShare`），单次最多 1 秒；算不完就和前台一样降低实际倍速，不会把机器占满
  - 倍速、暂停照常生效：暂停时后台什么都不做
- **回到页面**：离开期间过了 30 秒以上游戏时间时，提示“你不在的时候，蚁群从第 X 天 … 生活到了 …”
- **开关**：顶栏速度组里的“后台运行”，记在 `localStorage` 的 `cyber-ant-background`，属于玩家偏好，不进存档
- **不做的**：不在回到页面时一次性补算离开的时间。离开一小时就要补算 3600 模拟秒，1000 只蚂蚁约需半分钟以上，期间页面卡住；后台边走边算没有这个问题
- **限制**：浏览器在内存紧张时可能直接丢弃后台标签页，节能模式下也可能冻结耗 CPU 的后台页面，这时模拟还是会停（回来时页面重新载入，从最近一次自动保存继续）；手机浏览器切到后台通常会冻结页面

### T-026 沿边绕行带方向记忆
- **决定**：地表避障从“碰到就沿切线滑开”改为沿边绕行（`Ant.skirt`）：选定绕行方向后保持 1.5 秒；连续 3 秒没走出 3 cm 就换另一边（后来加了贴边和反向后保持，见 T-059）
- **原因**：玩家放的长树枝和自然石块会围出凹角，原来的做法每一步都按当前朝向重新选边，蚂蚁会在凹角里来回摆动、长时间卡住。测试中树枝的一端离侧入口 5 cm、旁边还有一块小石头，修正前最多 9 只同时卡住，修正后最多 3 只，且都会在几秒内脱困

### T-043 地表调亮，夜里看得清蚂蚁
- **需求**：地面上整体偏暗，夜里几乎认不出蚂蚁；地下透视反而很亮
- **原因**：透视地下时有一盏跟随相机的观察灯，地表没有；夜里地表只有很弱的月光（1.3）和天空光（0.55），黑色的蚂蚁落在深褐色地面上几乎没有对比。刚日落时月亮贴着地平线，平地照不到，比深夜还黑
- **决定**（数值在 `CONFIG.light`）
  - 白天：阳光 2.8 → 3.2，天空光 1.0 → 1.15，整体亮一些但不过曝
  - 夜里：月光 1.3 → 2.4，天空光 0.55 → 0.95 并偏月光蓝；地表也打开观察灯（冷白，强度 5，随天亮减弱到 0），让镜头附近的地面亮起来，黑色的蚂蚁就能分出轮廓
  - 月亮始终挂得较高，日落后和深夜一样亮
  - 透视地下的暖色观察灯不变，地下的观感和原来相近
- **保留夜色**：天空、星空、雾色不变，夜里仍是偏蓝的暗色调；雨夜因为云遮月和地面打湿会更暗一些

### T-044 触屏操作：地图式手势
- **需求**：手机上操作很困难。本轮只做操作，面板布局下一轮再做
- **不做虚拟摇杆**：这是观察类游戏，镜头要做的是“看那里、离近点、换个角度”，和地图应用一样；摇杆适合连续操控角色，在这里反而要一直按住，还会多盖住一块画面
- **手势**（`CameraController` 按 `pointerType === 'touch'` 分流，鼠标的处理不变）
  - 单指拖动：沿地面平移，手指下的地面跟着手指走（按视距和视角换算），镜头高度和朝向不变；跟随蚂蚁时改为绕着它转
  - 双指：先判断是“俯仰”还是“缩放 / 旋转”，判断前的移动在判断后一并补上。浏览器按手指分别发 `pointermove`，两指的位移总是一先一后，所以俯仰要求两指都向同一方向竖直移动超过 10 像素、间距和角度基本不变；否则间距变化超过 8%、角度变化超过 0.15 弧度或水平移动超过 14 像素就算缩放 / 旋转
  - 缩放 / 旋转：沿视线推近拉远（一步最多 40），并以两指中点下的地面为中心旋转、跟着中点平移；俯仰也以视线落在地面上的点为中心
- **点按**：按下到松开移动不超过 10 像素算点按，320 ms 内在 40 像素内再点一次算双击；浏览器为触屏补发的 `dblclick` 不再处理。触屏点选的容差 32 像素（鼠标 16），蚂蚁很小，手指盖住的范围大。手指下是房间或垃圾堆、容差内有蚂蚁时选蚂蚁（这两种范围大，很少需要专门选）
- **工具两步放置**：触屏没有悬停，看不到预览圈就放下去容易放错。点地面只记下位置（`ToolController.pending`）并在那里显示预览圈和原因，工具面板出现“放在这里”，点它才放下；可以再点别处改位置，树枝有“旋转”按钮。鼠标仍是点一下直接放
- **挡住浏览器手势**：画布 `touch-action: none`，页面 `touch-action: manipulation`、`overscroll-behavior: none`，iOS 再拦 `gesturestart`，避免双指缩放整个网页、下拉刷新和双击放大
- **限制**：手势手感只在无头 Chrome 的触屏模拟里测过，没有真机试过；面板布局下一轮再做，目前只把工具面板在窄屏上改为居中（原来固定在 520 像素右侧，手机上会跑出屏幕）

### T-045 手机布局
- **需求**：手机上大部分屏幕被界面挡住；要考虑横屏、竖屏，手机和平板
- **怎么分**：按视口尺寸而不是设备类型判断。宽小于 700 或高小于 500 用手机布局，横竖屏的手机都落在这里；平板（768 宽以上、高 500 以上）沿用桌面布局。窄的桌面窗口也会切到手机布局，鼠标照样能用。转屏、改窗口大小时重新判断，切换前后的开关状态不变
- **手机布局**（同一份 DOM 结构由 `Hud.renderStatic` 按布局写两种版本，按钮的 id 不变，`refresh` 不用区分）
  - 顶栏一行：时间、天气和温度（放不下时截断）、暂停、倍速菜单（含后台运行）、“更多”菜单（性能数字、帮助、存档、语言、GitHub）。竖屏不显示标题
  - 底栏五个按钮：蚁群、透视、视图、工具、事件。透视最常用，直接放在底栏上做开关；信息素、分工着色、草丛、统计收进“视图”；四种工具收进“工具”，每个按钮下面写出可选的东西
  - 抽屉：蚁群、视图、工具、事件、统计、存档、帮助都是抽屉，同一时间只开一个；再点一次底栏按钮或点画面就收起（这一下不会选中东西或放下工具），和地图应用一样。帮助开局打开，25 秒后或第一次选中东西时收起
  - 信息面板：选中东西后从下方弹出，没有抽屉、不在用工具时才显示，最高约六成屏幕，可以滚动；点标题折叠成名字和第一行（蚂蚁是当前行为）
  - 事件：画面空着时在底栏上方浮出最近两条，点了能飞过去；“事件”抽屉里是全部
  - 横屏：高度只有 400 左右，底栏改到左侧竖排，抽屉在它右边、从顶栏下沿往下排，信息面板在右侧，中间留出画面
  - 刘海屏：`viewport-fit=cover`，顶栏、底栏和侧边按 `env(safe-area-inset-*)` 让开
- **平板和桌面**：布局不变。触屏设备（`pointer: coarse`）按钮加大、不显示快捷键角标；蚁群面板点标题可以折叠成一行，竖屏平板上能多露出画面；统计面板在窗口窄时以不超出右边为准（原来 1000 宽以下会跑出屏幕）
- **定位方式**：面板位置原来由 `Hud.layout` 写内联样式，现在只写 CSS 变量（顶栏下沿、底栏高度、竖排底栏宽度、事件和图例高度），两种布局都由 CSS 排
- **不做的**：没有拖动抽屉改变高度的手柄；横屏时抽屉和信息面板也不同时显示
- **补充**：竖屏的触屏平板开局时蚁群面板先折起来。工具说明改成不分鼠标和触屏的说法（“点地面投放”），旋转树枝有按钮，说明里不再写 R 键；手机布局的帮助把“点击左下角的事件”换成底栏上方浮出的事件和“事件”抽屉

### T-046 手机和平板上的后台运行：只给说明
- **问题**：手机和平板的浏览器切到后台会冻结整个页面，Worker 也一起停，T-042 的后台运行在这些设备上不起作用；开关显示“开启”，玩家会以为离开时蚁群还在过日子
- **怎么认**：按浏览器标识认 iPhone、iPad、Android；iPadOS 的 Safari 自称 Mac，再用“Mac + 多点触控”补上（`BACKGROUND_LIMITED`）。这里看的是系统行为，所以按设备类型而不是按视口尺寸或 `pointer: coarse`：触屏笔记本切到后台照样能跑
- **做法**：这些设备上“后台运行”按钮变暗、虚线边框，不显示开启；点它只弹出说明（离开时蚁群会暂停，回来后接着生活；想让它一直过日子就让页面停在前台），不改开关。回到页面时如果离开了 1 分钟以上、蚁群没有在后台走（也没有暂停），提示“页面在后台被浏览器冻结了约 N 分钟，这段时间蚁群暂停了”
- **不做的**：不在回来时补算离开的时间，理由同 T-042；离开前的进度在 `pagehide` / `visibilitychange` 时已经自动保存，页面被系统回收后重新打开也能接上
- **顺带**：提示条的显示时间按文字长短算（每字 0.09 秒，2.2 到 6 秒），长的说明不会一闪而过

### T-047 画质自动调节与省电
- **问题**：渲染始终按像素比 2、2048 的阴影贴图、满帧率画。手机屏幕像素多、显卡弱，发热耗电；120 Hz 的屏幕还会画到每秒 120 帧；暂停时画面不动也照样满帧
- **画质档位**（`CONFIG.render.levels`）：高（像素比 2、阴影 2048）、中（1.5、1024）、低（1、1024）。只改这两项，因为能在运行中直接改：抗锯齿要重建 WebGL 上下文，阴影类型要重编所有着色器。阴影 1024 时每个阴影像素约 0.09 cm，蚂蚁的影子仍有十来个像素，看不出差别
- **自动**：电脑从高档开始，手机和平板（同 T-046 的识别）从中档开始。统计满帧率时段的平均帧率，连续两个 3 秒都低于 40 就降一档并提示。只降不升：升档后又卡就会来回跳；下次打开页面从默认档位重新开始。切回页面、编译着色器之类单帧超过 250 ms 的停顿和限帧时段不算
- **帧率上限**：平时 60（120 Hz 屏幕隔一帧画一次）；“省电”是低档加每秒 30 帧；暂停后 2 秒没有鼠标、触摸、滚轮、按键操作就降到每秒 15 帧，一有操作马上恢复，性能数字后面注明“暂停中，省电降帧”。跳过的帧什么都不做，下一帧的模拟时间照算，所以倍速不受影响
- **入口**：桌面顶栏右上角的“画质”按钮，点一下换一档（自动 → 高 → 中 → 低 → 省电）；手机在“更多”菜单里，五个选项排成一行。选择记在 `localStorage` 的 `cyber-ant-quality`，属于玩家偏好，不进存档
- **限制**：iOS 低电量模式会把页面限在每秒 30 帧，“自动”会把它当成卡顿降到低档（省电本来也是这时想要的）；模拟本身跟不上时（3000 只、20 倍速）降画质帮助不大，实际倍速照样会降
- **补充**：加了画质按钮后，768 宽的平板上英文顶栏放不下，存档、语言、GitHub 被挤出屏幕（T-048 一起修）。现在天气温度放不下时截断，1000 宽以下 GitHub 只留图标；`scripts/ui/layoutshots.mjs` 也检查顶栏里被挤出去的按钮

### T-048 添加到主屏幕（PWA）
- **需求**：手机上像应用一样从主屏幕打开，没有浏览器地址栏、有图标、断网也能玩
- **做法**：`public/` 下放清单（`manifest.webmanifest`）、离线缓存脚本（`sw.js`）和图标，构建时原样复制到 `dist/`，Cloudflare 一起发布。游戏本身仍是一个 HTML 文件
  - 显示方式 `standalone`：保留系统状态栏（时间、电量），iOS 状态栏半透明，界面已经按安全区域让开（T-045）。不用 `fullscreen`：安卓上全屏要从边缘划出才能退出，观察类游戏没必要
  - 图标是琥珀色底上的一只黑蚂蚁（`src/assets/icon.svg`），`scripts/tools/icons.mjs` 用无头 Chrome 画成 192、512、可裁切的 512 和 iOS 的 180 像素 PNG。网页标签上的小图标在构建时内联进 HTML，双击打开的单文件也有
  - 离线缓存：联网时总是取最新的页面并存一份，断网或 4 秒没响应时用存下的。不用“先缓存后更新”：那样发布新版后要打开两次才能看到。带不同网址参数（`?new=1` 等）的页面共用一份缓存。只缓存页面、清单和图标，其他请求不经过它
  - 只在正式构建、https 或本机上注册；开发服务器和双击打开的单文件（`file://`）都不注册
- **入口**：安卓 Chrome、Edge 会发出 `beforeinstallprompt`，“添加到主屏幕”点了直接弹出安装框；iOS 没有这个事件，点了提示从分享菜单添加。手机布局在“更多”菜单里，平板（桌面布局）放在操作帮助的末尾，免得挤占顶栏。电脑上不显示（浏览器地址栏自己有安装按钮），已经从主屏幕打开时也不显示
- **限制**：iOS 上从主屏幕打开的应用和 Safari 有各自的本地存储，存档不互通，提示里写明了；第一次要联网打开过才能离线；离线缓存只在本机无头 Chrome 里测过，iOS、安卓的真机安装没试过

### T-049 抽出框架：目录分层（框架重构第 1 步）
- **目的**：以后做同类产品（蜂巢 / 白蚁这类社会性昆虫、全 3D 鱼缸、地表生态）时尽量复用现有代码。形式定为同一个仓库里分层：`src/core` 是框架，`src/games/ant` 是蚂蚁游戏；不拆成独立的包，等第二个游戏真的做起来再说
- **怎么分**：和具体物种、玩法无关的放进 `core`：随机数和数学、文字翻译的机制、设备识别、添加到主屏幕、后台运行、语言选择、存档槽、游戏时钟、空间哈希、天空光照、雨、画质、相机。其余（配置、词典、蚂蚁、蚁群、蚁穴、世界和各子系统、蚂蚁和物品的渲染、界面面板、点选、工具）放进 `games/ant`。`terrain.ts`、`pheromone.ts` 这类以后可能复用的先留在游戏里，等空间接口（第 4 步）定下来再搬
- **依赖方向**：只能游戏依赖框架。`scripts/core/layercheck.mjs` 检查 `core` 有没有导入 `games/` 或 `main.ts`，以及游戏之间互相导入。当时的 9 处反向依赖（框架读蚂蚁的配置和词典，`spatial` 用 `Ant` 类型，`saveSlot` 用存档类型，`rain` 用天气类型）列在脚本的 `PENDING` 里，拆掉了没删掉也报错；第 2 步全部拆掉（T-050）
- **这一步只搬文件、改导入路径**，不改逻辑。为了验证后面会动更新顺序的步骤，`Rng` 加了 `reseed`，`simtest` 读环境变量 `SIM_SEED`：同一种子两次运行除耗时外逐行相同，重构前后用它对比。游戏本身仍用当前时间做种子
- **后续步骤**：2 词典和配置拆成框架部分与游戏部分；3 模拟内核（子系统列表、事件记录、存档注册，时钟去掉土壤模型）；4 空间接口（高度场、体积），相机、点选、工具都通过它；5 实体注册表和视图层（透视由游戏声明）；6 界面拆成外壳和游戏面板，`main.ts` 只组装一个游戏模块；7 运动方式拆成模块（地表行走、隧道网络行走）；8 做一个最小的鱼缸示例检验边界，要求游戏代码少于 1500 行、不改框架里为蚂蚁写的部分；9 写框架说明和文档模板
- **不做的**：三维场（体积里的温度、信息素）、多人、运行时加载插件、一个页面里放多个游戏

### T-050 框架不读游戏的配置和词典（框架重构第 2 步）
- **配置**：主循环（固定步长、每帧最多步数、帧预算）、后台运行、画质、自动保存间隔和物种玩法无关，移到 `src/core/config.ts` 的 `ENGINE`；一天多长、几点开局、光照强度仍在游戏的 `CONFIG`，由游戏在构造时传给 `SimClock` 和 `Environment`。框架的其他依赖也改成由游戏传入：`SpatialHash<T>` 只要求有 `pos`、`alive`；`SaveSlot<D, M>` 的存档键、存档和摘要的类型由游戏给（蚂蚁游戏仍用 `cyber-ant-save`，旧存档照常读）；`RainView.sync` 直接收雨势；页面标题由 `main.ts` 设置
- **词典**：框架自己用到的 4 条（原样显示、游戏时刻、两种存档失败原因）放在 `core/i18n`，其余 578 条留在游戏。键的类型 `Messages` 用 TypeScript 的声明合并：框架只声明自己的键，游戏的 `i18n/index.ts` 用 `declare module` 补上自己的，`L('键')` 写错照样编译报错，英文缺键也照样报错（每份英文词典的类型是对应中文词典的键）。游戏的词典在加载时用 `registerDicts` 并进去，键重名直接报错
  - 没有选“框架定义一个总表、游戏往里填”：总表得知道每个游戏的键，框架就又依赖游戏了
  - 没有选“键用普通 string”：五百多个键写错了只能靠运行时发现
- **登记时机**：`games/ant/config.ts` 导入游戏的词典模块。游戏的每个模块都读配置，脚本也都通过 `World` 间接导入它，所以第一次翻译之前一定已经登记。第 6 步有了游戏模块声明后改为由入口显式登记
- **结果**：`scripts/core/layercheck.mjs` 的待拆名单清空，框架代码不再导入任何游戏代码。`SIM_SEED=7` 的 5 天模拟与第 1 步逐行相同

### T-051 模拟内核：子系统列表、存档登记、事件记录（框架重构第 3 步）
- **`core/sim/simulation.ts` 的 `Simulation`**：时钟、`advance`（固定步长、帧预算、实际倍速，原来在 `World`）、子系统列表、存档登记、最近事件。`World` 继承它，在构造函数里登记：
  - 每步更新的顺序（`addSystem`）：天气 → 蚁群 → 天敌 → 警报 → 食物 → 蚜虫 → 水洼 → 信息素，和原来 `tick` 里写死的一样
  - 存档的各部分（`saves.add(字段名, 保存, 恢复, 可选)`），登记顺序就是读档顺序：时钟（内核自己登记）→ 蚁穴 → 玩家障碍物 → 水洼 → 天敌（可选）→ 天气（可选）→ 食物源 → 蚜虫 → 信息素 → 蚁群。`saveWorld` / `loadWorld` 只剩存档头和版本、种子检查
- **存档格式不变**：字段名和内容都没变，只是 JSON 里字段的先后不同。用上一版代码生成一个下雨中、有玩家障碍物和投放食物的存档，新代码读入后时刻、蚂蚁数、房间数、事件、障碍物、天气都对得上，再存一次的字段集合相同，继续跑 300 秒正常
- **事件**：`Colony.pushEvent` 改为 `World.events`（`EventLog<EventRef>`），对象的位置仍由 `Colony.refPos` 提供（第 5 步交给实体注册表）。存档里事件仍放在蚁群下面
- **土壤模型**：`SimClock` 只管时刻和昼夜；土壤温湿度和天气写入的降温、湿润度移到蚂蚁游戏的 `world/soil.ts`（`World.soil`）。鱼缸之类的游戏不需要它，地表生态类以后可以复制或再抽出来
- **类型检查覆盖脚本**：这一步改名时 `weathertest` 还在用 `colony.pushEvent`，`tsc` 只查 `src/` 没发现。加了 `tsconfig.scripts.json` 和 `@types/node`，`npm run typecheck` 同时检查 `scripts/`；顺带发现 `tooltest` 放石块时漏了角度参数
- **结果**：`SIM_SEED=7` 的 5 天模拟与重构前逐行相同

### T-052 空间接口（框架重构第 4 步）
- **`core/space/space.ts` 的 `Space`**：相机能去的范围 `cameraBox`、某处的表面高度 `surfaceAt`、视线和表面的交点 `raycast`。相机（离地高度、平移和活动范围的限制）、点选（鼠标下的地面点）、工具的放置点、雨丝溅水圈和注视点都通过它，不再直接调用 `Terrain.heightAt`
- **`HeightfieldSpace`**：一张高度场的地面，求交沿视线步进再二分，就是原来 `Picker.groundPoint` 的做法（T-024），交点超出地图范围返回空。蚂蚁游戏在 `games/ant/space.ts` 里用地形高度和 `CONFIG.world.cameraRange / cameraMinY / cameraMaxY` 构造；这三个数原来写死在 `camera.ts` 里
- **不进 Space 的**：透视地下（相机在地面以下时切换）和选中对象的位置仍由蚂蚁游戏处理，第 5 步交给实体注册表和视图层。鱼缸这类全 3D 的游戏另写一个体积空间，交点取在缸壁或底沙上
- **框架层单元测试**：新增 `scripts/core/coretest.ts`，不依赖任何游戏，覆盖高度场求交、存档登记的顺序和可选部分、事件记录、模拟内核的子系统顺序和每帧步数上限、词典重名
- **结果**：`SIM_SEED=7` 的 5 天模拟与重构前逐行相同；触屏和鼠标测试（平移、缩放、放工具）通过

### T-053 实体注册表（框架重构第 5 步）
- **问题**：“某个对象现在在哪”原来写了两遍：`main.ts` 的 `selectionPos`（选中后飞过去）和 `Colony.refPos`（事件定位），两边各有一个按类型的分支，内容还不完全一样。飞过去的距离、能否跟随、哪些对象读档后编号会变，也分散在 `main.ts` 和 `colony.ts` 里
- **`core/sim/entities.ts` 的 `EntityRegistry`**：游戏为每类对象登记 `pos`（不在了返回 null；可跟随的要返回对象自己的位置）、`viewDistance`（默认 14）、`follow`、`unstable`（读档后编号会重新分配，事件存档时只留位置）。`Simulation` 自带一个注册表，事件定位默认查它
- **蚂蚁游戏**：`games/ant/world/entities.ts` 定义 `GameRef`（原来的 `Selection` 和 `EventRef` 合成一个）并登记 10 类对象。蚂蚁可跟随、观察距离 6，房间 26；食物源、天敌、玩家障碍物、水洼不稳定。`main.ts` 里选中、飞过去、跟随、点击事件、注视点、`?select=` 都不再按类型分支
- **合并后界面上的变化**：两份位置原来不一致的地方取选中时的那份，所以寄主植物的事件位置改在蚜虫群那一段茎秆上；原来选中后飞不过去的玩家障碍物和水洼现在能飞过去；`?select=` 接受所有登记过的类型。模拟不受影响
- **没有进注册表的**：点选（蚂蚁按屏幕距离，其他物体按射线，房间和垃圾堆让给蚂蚁）和信息面板仍按类型写在 `picking.ts` 和 `hud.ts`，第 6 步拆 HUD 时把信息面板改成按类型登记；透视地下等视图开关也放到第 6 步
- **相机**：`follow`、`flyTo` 接受任何 `{x, y, z}`，注册表里的位置可以直接传进去
- **测试**：`coretest` 加了注册表的 3 项；新增 `scripts/ui/selecttest.mjs`，在页面里检查跟随、按 F 取消、飞到房间的距离、点击事件后飞到对象旁边
- **结果**：`SIM_SEED=7` 的 5 天模拟与重构前逐行相同

### T-054 游戏模块与界面外壳（框架重构第 6 步）
- **问题**：`main.ts`（575 行）和 `hud.ts`（962 行）混着两类东西：任何模拟游戏都要的（启动、读档、自动保存、选中跟随、按键、网址参数、后台运行、主循环、顶栏、抽屉、事件列表、存档面板、帮助、语言、画质）和只有蚂蚁有的（场景对象、透视和信息素视图、蚁群概况、10 种信息面板、统计曲线）。换一个游戏只能整份复制再改
- **`GameModule`**（`core/app/game.ts`）：游戏声明标题、相机、存档读写、空间，`mount` 搭好场景后返回 `GameSession`。`runApp(game)` 是通用的启动和主循环，`main.ts` 只剩一行
- **视图开关由游戏声明**（`ViewToggle`）：名字、按键、`?view=` 用的名字、手机底栏图标、当前状态、切换。外壳按这张表生成顶栏按钮、视图面板、按键；“统计”在游戏提供 `ui.stats` 时由外壳自己加上。透视的“被迫打开”（相机在地下、跟随的蚂蚁在巢里）只是蚂蚁游戏的 `on()` 返回真
- **信息面板按类型登记**（`InfoPanels<R>`）：映射类型要求实体的每种 `kind` 都有一个渲染函数，漏了编译不过；外壳在面板下统一加“取消选择”

- **框架文字**：外壳用到的 85 条移进框架词典，措辞改成不提蚂蚁（“先选中一个可以跟随的对象”）；蚂蚁游戏用 `registerDicts` 的第二个参数改写回原来的说法，只能改写框架已有的键。`i18ncheck` 新增两项：`src/core` 里不能出现游戏词典的键，改写不能改占位符

- **没做的**：词典仍在导入游戏配置时登记（不放进 `GameModule`），因为无界面脚本不经过 `runApp` 也要用；`Picker` 仍是蚂蚁游戏的（蚂蚁按屏幕距离、其他按射线），等鱼缸示例看清共性再说
- **结果**：`SIM_SEED=7` 跑 5 天模拟，输出与重构前逐行相同；界面截图与之前一致

### T-055 运动方式拆成模块（框架重构第 7 步）

- **唯一的变化**：一步跨过节点时，步态相位原来按每段的剩余步长重复累加，现在按实际走过的距离算。只影响腿的摆动相位，模拟不读它

### T-057 一键检查与持续集成
- **问题**：十几个测试脚本各跑各的，多数只打印结果、要人逐行看；“重构前后输出逐行相同”要手动跑两次再比；改了框架要记得回归两个游戏
- **决定**：
  - 每个无界面测试自己判断通过与否，失败时退出码非零；`scripts/check.mjs` 按顺序跑完并汇总
  - 模拟基线文件进仓库，比对时去掉耗时。基线变化随提交一起出现在差异里，审查时能看到行为改了哪些指标
  - 分三档：`check:fast`（约 10 秒，改动中途用）、`check`（约 3 分钟，提交前）、`check:ui`（约 6 分钟，要浏览器，改界面时）。GitHub Actions 只跑 `check`：浏览器测试依赖软件渲染和本机字体，在 CI 上容易不稳定，先不放
  - 通过条件按“不能更差”定，不是按当前精确值：比如防御只要求三只狼蛛都引来增援并离开，不规定几秒；精确的回归由模拟基线负责

### T-058 随机数和编号归世界所有
- **问题**：蚂蚁行为用的是模块级的共享随机数，以启动时间为种子，不进存档；对象编号也是模块级计数器。结果：同一个存档读两次跑出来不一样，测试只能靠环境变量重设种子；同一进程里的两个世界（读档测试）互相抢随机数和编号
- **决定**：
  - 随机数和编号都放进模拟内核：`Simulation.rng`（构造时传世界编号）和 `Simulation.ids`（`IdPool`，每类对象一个计数）。内核自己存档，游戏不用管
  - 用 `SaveRegistry.addLast` 在其他部分之后恢复：别的部分恢复时可能要新建对象、抽随机数（比如重建网格、新建蚂蚁时的随机初值），它们抽掉的数和发掉的号在最后被覆盖回存档时的状态。旧存档没有这两项，随机数沿用新世界生成后的状态，编号按读进来的最大值往后发
  - 编号计数恢复成存档里的值，而不是“已有对象的最大编号加一”：死掉的蚂蚁也占过号，只有恢复原值，读档后发的号才和不存档一直跑时一样
  - 只影响画面的随机（雨滴、叶子抖动、物品的朝向初值）继续用 `Math.random`
- **还没做到**：读档后的世界和一直跑的世界仍会分开，因为任务协程、警报、增援这些短暂状态不进存档（T-027）。行为协程内核整理时（读档后任务从中途继续）再往这个方向走
- **结果**：同一个存档读两次、各跑 1200 秒，所有指标完全相同（`savetest` 检查）；`simtest` 不再需要 `SIM_SEED`，基线重新录制；性能不变。存档往返的“物品数”暂时允许相差搬运中的件数，读档后任务能从中途恢复时（行为协程内核整理时）改为精确相等

### T-059 行为协程内核进框架；读档后接着送手里的东西
- **问题**：“生成器下达指令、运动层逐帧执行、结果传回生成器”这套调度写在 `Ant.update` 里，四个字段（`routine`、`cmd`、`cmdInit`、`result`）散在蚂蚁身上，别的游戏想用得照抄。读档时正在搬运的物品直接瞬移到目的地，存档往返的物品数对不上，储食室凭空多出几十份
- **决定**：
  - `core/sim/behavior.ts` 的 `Behavior<C>`：`run(下一个协程, 执行一条指令, 每帧最多几条)`、`abort`，字段 `routine`、`cmd`、`started`、`result`。蚂蚁用 `Ant.behavior`，调度顺序和原来逐行相同（重构后基线不变）
  - 协程仍然不存档（生成器不能序列化，T-027）。改成“读档后从送货这一步重新开始”：蚂蚁存档时记下手里物品的编号（`carry`），读档后物品还在它嘴里；`Colony.newRoutine` 看到蚂蚁拿着东西，先交给 `finishCarry`，按物品种类调用和原任务同一段送货子协程（`storeCarriedFood`、`dumpSoil`、`takeOut`、`deliverWasteInside`、`deliverBrood`，从原任务里拆出来，原任务用 `yield*` 调用）
  - 没考虑“把指令也存下来、读档后从那条指令继续”：协程里指令之前的局部变量（要去哪个房间、拿的是谁的）照样丢了，恢复出来的半截任务反而更难保证一致
- **顺带修的寻路问题**：`savetest` 加了“读档后 300 秒内手里的东西都要送到”，抓到一只返巢觅食蚁在测试树枝旁来回走、一直进不了巢。树枝一端和一块自然石头围出凹角，另一端被水洼堵住，目标（侧入口）正好在树枝背后。原来碰到障碍只沿切线滑一步，下一步就转回目标，凹角里永远来回；被困反向后，离开障碍再碰上又按朝向重选，被目标拉回原处。改为：
  - 贴边：正在绕行、而且朝目标方向 2.5 cm 以内还挡着时，不转向目标，而是朝障碍一侧弯着走（`Skirt.hug`，2.5 弧度/秒），碰到再改成切线，像沿墙摸着走；连续贴边 25 秒后放弃，回到直接朝目标走
  - 被困反向后保持新方向 20 秒，途中离开障碍再碰上也不重选
  - 树枝是一串小圆，沿一个圆的切线会撞进下一个圆、被推回凹口；这时改沿两圆中点的切线滑过去
- **结果**：存档往返的所有计数（含物品）改回精确相等；下雨中途存档的 51 件、晴天的 152 件搬运中物品读档后全部送到。寻路改动后基线重录：5 天后 1045 只（原来 1048），收集食物 2180 份（原来 2042），其余在日常波动范围内

### T-060 大文件按职责拆开
- **问题**：`ant.ts`、`colony.ts`、`routines.ts` 各 800–1000 行，找一段地表寻路或者某个职别的任务要在长文件里翻；改一个职别的任务时，差异里混着别的职别
- **决定**：
  - 蚂蚁的运动层按“巢内 / 地表”拆成两个模块，写成普通函数（`stepGoto(a, dt, w, node)`），不用 mixin 或子对象：调用处和原来的方法一样直接，V8 照样内联；代价是它们用到的字段不能再标 `private`，改为在 `Ant` 里按文件分组注明
  - 行为协程按职别分文件，共用片段放 `common.ts`；`index.ts` 只放入口和读档后的收尾
  - `Colony` 留下状态、物品放置（各个索引必须经过它）、食物、生命周期、每步推进；个体之间的互动和幼体 / 储食的日常变化拆出去，同样是以蚁群为第一个参数的函数
  - 拆分是纯搬运：基线必须逐行不变，这是判断有没有搬错的依据
- **结果**：最大的文件从 976 行降到 720 行（`colony.ts`），其余都在 480 行以内；基线不变，性能不变

### T-061 入口受威胁时立刻调派警戒
- **问题**：内务蚁只在选新任务时才看入口有没有威胁，手头的任务（搬垃圾、挖掘）常常要几十秒，所以入口警戒比威胁晚 17–40 秒出现；警戒任务一开始就定好巡逻 25–60 秒，狼蛛早走了还在外面转，加上增援状态要等增援时间到才结束，最长的在威胁解除后 80 秒才回巢
- **决定**：
  - 入口刚变成受威胁时（`PredatorManager.update` 里威胁入口从无到有），`callGuards` 从在巢里、空手、没在封堵入口的内务蚁中按巢内路程挑最近的 8 只（总数不超过 24），用框架新增的 `Behavior.start` 打断当前任务，直接换成警戒任务。只挑空手的，免得手里的东西被扔在半路
  - 警戒任务分成一段段巡逻（T-062 改为 2 秒一段），每段结束看一眼威胁还在不在，不在就回巢
  - 增援中的工蚁附近没有狼蛛、闻到的警报也低于响应阈值时，增援最多再持续 4 秒（`calmSec`），不再等满 15–30 秒
- **结果**：`defensetest` 里威胁出现后 1–3 秒就有 3 只在入口外警戒，威胁解除后 22–30 秒全部回巢。剩下的时间是围攻处的警报在散（半衰期 6 秒，从上限降到响应阈值约 20 秒），闻得到警报的工蚁继续在原地搜寻，这是想要的。测试门槛改为 10 秒内出来、35 秒内回巢（T-062 改为检查每只的闲逛时间）。基线重录：5 天后 1046 只（原来 1045）

### T-062 发觉靠近的狼蛛提前躲开
- **问题**：蚂蚁只对警报有反应，同伴被扑击之前不会理会正在走近的狼蛛，迎面走过去送死
- **决定**：
  - 地表工蚁每 0.5 秒检查警报时，没闻到警报就看 10 cm 以内有没有还在捕猎的狼蛛（进食、离开中的不算）。狼蛛走动时每次 35% 发觉，静止伏击时 8%。发觉后由 `Ant.flee` 接管 2–4 秒，朝远离狼蛛的方向以 1.25 倍速跑开；和增援一样不动协程，跑完接着原来的指令。闻到警报就改去增援
  - 爬在植物上、陷在坑里、正在警戒的不躲：警戒蚁就是出来迎击的
  - 发觉距离只比狼蛛发现蚂蚁的 7 cm 远一点，而且不是每次都能发觉：狼蛛视力好、蚂蚁主要靠振动，迎面走近时多半还是狼蛛先扑。太远太灵会让狼蛛几乎抓不到蚂蚁
- **顺带修的问题**：
  - 被 `callGuards` 临时调派的内务蚁如果正在隧道里往深处走，要走完这一段才能掉头，有的来回要十几秒。`GraphWalker.advance` 改为：走到半路换了目标、而新路线要从出发的那端走，就地掉头
  - 从巢深处出发的警戒蚁走到入口时威胁可能已经解除，原来照样出去巡逻一段，威胁解除后 50 秒还陆续有警戒蚁出巢。改为先走到那个入口，威胁还在才出去；巡逻每段从 5 秒缩短为 2 秒
- **结果**：`defensetest` 新增“狼蛛走近觅食路线”，第一次扑击前有 4 次发觉而躲开；巢口的狼蛛周围最多 15–19 只同时躲开。警戒蚁威胁出现后 1–7 秒到位，威胁解除后每只最多再闲逛 2–3 秒（之后的时间在追打狼蛛、搜寻警报源，等警报散掉）。测试改为检查每只的闲逛时间（≤ 8 秒）。基线重录：5 天后 1050 只（原来 1046），被捕食 19 只（原来 25；只关掉躲避的同一版本是 24）

### T-063 3000 只时休息室和蚁丘的拥挤
- **问题**：3000 只开局时蚁穴只有 1000 只的大小。夜里几乎所有蚂蚁都挤进两间休息室，最挤的一间 5.4 只/cm²（可走地板上约 2.8 只就挤满了），休息室、越冬室、储食室合计约 1250 对重叠；白天在入口外警戒、闲逛的蚂蚁都在同样的 4–5 cm 范围里，巢口 15 cm 内重叠 600–670 对
- **决定**：
  - 蚁群每步统计一次各房间的只数（在房间里的，加上正要去那间的），选休息室时那间超过 2.2 只/cm²（`crowd.restDensity`）就改去越冬室、储食室里最不挤的一间
  - 同时统计每个入口外有多少只在警戒、闲逛（按巡逻指令的中心归到最近的入口，不按位置数，否则散得越开数得越少）。超过 120 只（`crowd.moundRef`）时，巡逻和闲逛的范围按 √(只数 / 120) 放大，新来的蚂蚁也只有 1/倍数 的机会留在蚁丘上，其余去做别的：蚁群大了蚁丘也大
  - 巡逻原来是在中心附近随机游走，范围放大了也散不开；改为走到范围里的一个随机点、停 0.5–3 秒、再换一个点。随机点偏向中心（半径均匀取，不按面积），均匀分布时巡逻蚁散到觅食路线上，5 天被捕食从 19 只升到 32 只
- **没有做的**：隧道里的重叠从约 480 对涨到 1500–2800 对，是蚂蚁不再挤在休息室、改走更远的路去别的房间造成的。隧道宽度和路线是挖掘决定的，要等蚁穴按人口扩建才能真正解决，记在已知问题里
- **测试**：
  - 新增 `crowdtest`：3000 只跑一天，检查休息室最挤不超过 2.6 只/cm²、巢口 15 cm 内重叠不超过 300 对
  - `savetest` 的信息素总量改为允许差 0.5%：存档按 8 位量化，四舍五入后的总量偶尔差 1，以前是碰巧相同
  - `defensetest` 热身改为 800 秒（第二天下午）：500 秒是凌晨 3 点半，地表最密集处只有 2 只。狼蛛 7 cm 就扑、蚂蚁 10 cm 才察觉，扑中一只就停下吃，单看“走近觅食路线”那一段躲开几次全凭运气，改为所有场景合计至少 10 次；狼蛛又走回入口附近时出来的警戒蚁不算闲逛；警戒到位门槛放回 15 秒（白天内务蚁大多在外面干活，侧入口要 9–11 秒）
- **结果**：3000 只时最挤的休息室 2.3 只/cm²，三间房合计重叠约 480 对；巢口 15 cm 内重叠 146–237 对。1000 只的基线重录：5 天后 1049 只（原来 1050），被捕食 21 只（原来 19），死亡 47 只。性能不变（33 ms/s）

### T-064 触屏上拖动工具预览圈
- **问题**：手指没有悬停，触屏上点地面后预览圈就固定在那里，想挪一点只能再点一次，点偏了看不出来
- **决定**：
  - 选好位置后，单指按在预览圈上（圈的半径以内，至少 48 像素）拖动，预览圈跟着手指走，颜色和原因提示照常更新；在圈外拖动仍然平移镜头，第二根手指落下就交还给镜头的双指手势
  - 框架的 `CameraController` 加 `onTouchDragStart` / `onTouchDrag`：单指按下时问一次调用方要不要认领这次拖动。相机不知道工具的存在，认领规则在 `app.ts` 里
  - 不做“按住不放直接拖出预览”：单指拖动已经是平移，长按再拖要多等一下，还容易和平移混淆
- **结果**：`touchtest` 新增两项（拖动预览圈时预览跟着手指、镜头不动；圈外拖动仍平移）。顺带修了测试本身：原来固定点 (195, 500) 放食物，镜头飞到蚂蚁旁后那里正好有石块，改为换几个点直到预览圈变绿

### T-065 蚁穴按开局人口生成；减少巢内长途往返
- **问题**：3000 只开局时隧道里重叠 1500–2800 对，八成出在主竖井：5 段竖井里同时有约 1100 只，每 cm 约 15 只。统计竖井里蚂蚁在做什么：约 200 只觅食蚁“前往越冬室”（T-063 让休息室挤满的蚂蚁去最空的房间，而最空的是最深的越冬室，76 cm）、约 250 只觅食蚁去休息室和储食室、约 400 只内务蚁随机挑房间巡视，常横穿整个蚁穴
- **试过的**：只把竖井加宽到 2 倍、隧道 1.6 倍，竖井重叠只少约 40%；同时在路上的蚂蚁太多，加宽解决不了
- **决定**：
  - 开局多于 1000 只时（`?ants=`），`Nest.generate` 每多 200 只多挖一间工蚁休息室，从最浅的三个分岔点找空位；放不下先离分岔点远一些（隧道长一点），再逐渐往深处。主竖井半径按 √(只数 / 1000) 加宽，最多 1.7 倍。新的这一步排在原来的生成之后，1000 只时不取随机数，种子相同的蚁穴和原来完全一样
  - 休息室挤满时去最近的没挤满的房间（工蚁休息室、越冬室、储食室），都挤满了才去最空的那间；还没挖完的休息室不去
  - 内务蚁巡视和选休息室一样：随机挑两间，去巢内路程较近的一间
  - 游戏中途扩建工蚁休息室时，先在浅处的分岔点找地方
- **没有做的**：游戏中途隧道不随交通量加宽；第二条竖井、第三个入口。1000 只的蚁群自然长到 3000 只要很久（5 天只多几十只），扩建能跟上；只有直接以 3000 只开局时才挤
- **结果**：3000 只开局多出 10 间休息室（深 7–64 cm），隧道里重叠 720–1190 对（原来 1500–2800），休息室最挤 1.4 只/cm²（原来 2.3），巢口附近最多 206 对。`crowdtest` 加上隧道重叠不超过 1500 对。1000 只的基线重录：5 天后 1040 只（原来 1049），被捕食 27 只（原来 21），死亡 54 只；性能不变（同一时段改动前后都是 39–41 ms/s）。`defensetest` 放狼蛛的那一点被占着时在附近换个点

### T-066 瓢虫与蚜虫数量的自然涨落
- **问题**：蚜虫群只按逻辑斯蒂曲线增长，蚂蚁照料了九成以上的时间，5 天里每群都只涨不落，10 天后贴着上限 80 只。“蚂蚁保护蚜虫”（T-017）在画面上看不出来
- **决定**：
  - 新增 `LadybugManager`（`world/ladybugs.ts`）：晴天白天、气温不低于 12°C 时，平均每天飞来 2.5 只（同时最多 3 只），挑至少 12 只的蚜虫群，按只数平方加权（瓢虫循着植物受害的气味找来）。每天能吃 150 只，吃够 15–30 只或蚜虫少于 8 只就飞走；转阴下雨时也飞走
  - 驱赶：每 0.5 秒数一次爬在这株植物上的工蚁 n，吃的速度乘 1 / (1 + 0.5n)，驱赶量每秒加 n，累计到 60 就被赶走；没有工蚁时每秒恢复 0.5。瓢虫不单独结算碰撞，“爬在这株植物上”就算在追咬它，和狼蛛的 `harass` 同一种写法
  - 蚂蚁的反应：照料蚜虫时那群上有瓢虫，就留 15–30 秒驱赶（`act.chaseLadybug`）；挑蚜虫群时被攻击的那群权重加 3
  - 蚜虫太挤时生出有翅蚜迁飞：达到 56 只（上限的 0.7）开始，每天飞走 1.5 倍的比例、不再增殖，降到 32 只为止。这是真实的密度调节（拥挤和寄主植物营养变差都诱导有翅型），也是 5 天内能看出涨落的主要原因；瓢虫在被照料的蚜虫群上吃不了几只
  - 无人照料的蚜虫群另外每天减少 4%（原来写死 8%，草蛉、寄生蜂），瓢虫的捕食单独结算
  - 瓢虫不是可选中的对象：点它选中所在的植物，植物信息里显示瓢虫在做什么和累计被吃掉的只数。天敌工具加“瓢虫”一项，放在 6 cm 内最近的蚜虫群上；“赶走”附近没有狼蛛、蚁狮时赶走瓢虫
  - 存档：瓢虫和蚜虫的迁飞状态是可选的存档段 / 字段，旧存档读进来没有瓢虫
- **顺带修的**：入口受威胁时 `callGuards` 只从巢里挑内务蚁，正在入口外日常巡逻的反而不响应；而且警戒上限只数地表上的，巢里赶往入口的不限数量，40 多只一起挤进侧入口的隧道，20 秒都出不去。改为先挑入口 15 cm 内正在日常巡逻的（就地转为警戒），上限按所有在警戒任务里的工蚁数（`PredatorManager.guardsAll`）
- **结果**：`ladybugtest` 自然运行 7 天，瓢虫来 8 次、全被赶走，共吃 11 只；每群蚜虫都在 56 只左右迁飞，回落 24 只后再涨。对照：往照料最多的一群放一只胃口不限的瓢虫，15–36 秒被赶走，吃 0–4 只；往开局时还没被发现的最远一群放，83 秒吃掉 20 只（27 只剩 7 只）后自己飞走。`defensetest` 热身 700 / 800 / 950 秒都在 0–14 秒内有 3 只出来警戒。基线重录：5 天后 1037 只（原来 1040），被捕食 32 只

### T-067 读档后接着做正在做的那一步
- **问题**：读档后每只蚂蚁都从新任务开始（T-027、T-059）：走在隧道中途的放回最近的节点，爬在植物上的放回地面，步速、隧道里靠右的程度这些构造时抽的个体差异也重新抽。读档那一刻画面上一千只蚂蚁同时瞬移、换方向；和不存档一直跑的世界相比，5 秒后只有 7% 的蚂蚁还在 1 cm 以内
- **决定**：
  - 存下当前这条指令和它的执行进度（`AntSave.step`）：指令本身、是否已开始、活动说明、计时、巡逻和停顿的计时、局部和导航目标、要去的入口、路线噪声、爬植物的进度，隧道里的再加上 `GraphWalker` 的位置（所在的边、从哪端走、走了多远、目标节点）。读档时用框架新增的 `Behavior.resume(指令, 已开始)` 接着执行这一条，做完后才开新任务；拿着东西的仍先 `finishCarry`
  - 另存个体差异和计时（`ind`）、几十秒内的短暂状态（`fx`：增援、躲避狼蛛、原地停留、陷在蚁狮坑里、记着要绕开的坑、蹚水），以及蚁群的几个周期计时（`ColonySave.clocks`：每步计数、上次缺粮的日子、几项按间隔执行的检查）
  - 框架只加两样通用的：`GraphWalker.toSave` / `restore`（边按下标存）和 `Behavior.resume`。指令怎么存、进度有哪些字段由游戏决定
  - 都是可选字段：旧存档没有时照原来的办法（放回节点、重新抽）
- **仍然做不到完全接上**：协程里指令之前的局部变量（要去哪个房间、下一步做什么）存不下来，做完这一步后新任务和原世界的不同；所有个体共用世界的随机数，一只蚂蚁多取或少取一次，之后所有人取到的数都错开。所以只能保证读档那一刻不跳、这一步接着做完，之后两个世界逐渐分开。警戒、封堵入口、挖掘的认领、物品认领、照顾蚁后这些和任务绑在一起的关系仍在读档时清掉，做完当前这一步就重新选
- **结果**：`savetest` 加了接续检查：读档后没有一只蚂蚁的位置变了、活动说明全部相同、爬在植物上的只数相同；再跑 5 秒，和原世界相差不到 1 cm 的晴天 616/1021 只、下雨中途 710/1020 只（不接着做时 74 只和 69 只），要求至少一半。走散的大多是在房间里闲逛、巡逻的：它们每停一下就随机挑下一个点，随机数一错开就不同。存档大了约 6%（1000 只的世界 1345 → 1428 KB）。不影响一直运行的世界，基线不变
